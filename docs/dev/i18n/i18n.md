# WUtils Internationalization

`i18n` is WUtils' internationalization toolkit for Bukkit/Paper plugins: it loads
per-language string files (YAML, JSON, or a flat `.lang` format), resolves a raw string
or list of strings at a dotted path, and turns the result into an Adventure `Component`
through a pluggable interpreter (legacy `&`-codes, MiniMessage, or EnhancedLegacyText),
with optional PlaceholderAPI expansion and per-player language selection.

- Directory: `i18n/`
- Gradle project: `:WUtils-i18n`
- Maven artifact: `io.github.wyne10:wutils-i18n`
- Version: `5.6.1`
- Root packages: `me.wyne.wutils.i18n` (this page), `me.wyne.wutils.i18n.language` and its
  sub-packages (see [Package inventory](#package-inventory) below)

Source of these facts: `i18n/build.gradle`. `i18n` has **no dependency on any other
WUtils module**. Its `publish` Gradle task is finalized by
`:WUtils-i18n-kotlin:publish`, so the Kotlin companion module (`i18nKt/`, two files) is
always published alongside it — `i18nKt` will get its own wiki page separately. The
`configurables` module (not yet documented) has a `compileOnly` dependency on `i18n`.

## Entry points: `I18n` and its builders

`I18n` (`i18n/src/main/java/me/wyne/wutils/i18n/I18n.java:37`) is the runtime object a
consumer holds: it wraps the loaded `Language` map, the default language, the
configured `StringInterpreter`/`ComponentInterpreter` pair, and a `ComponentAudiences`.
It is built, not constructed directly — via `BaseI18nBuilder<T>` or its plugin-aware
subclass `PluginI18nBuilder`.

`BaseI18nBuilder<T extends BaseI18nBuilder<?>>`
(`i18n/src/main/java/me/wyne/wutils/i18n/BaseI18nBuilder.java:37`) is self-typed so its
fluent setters (`setLogger`, `setComponentAudience`, `setStringInterpreter`,
`setComponentInterpreter`, `setDefaultLanguageCode`, `setUsePlayerLanguage`) return the
concrete subclass without a cast. Its defaults: `PaperComponentAudiences`,
`BaseInterpreter`/`LegacyInterpreter` both validated with `EmptyValidator`, and
`usePlayerLanguage = true`.

Language loading, on `BaseI18nBuilder`:

- **`loadLanguage(File)` / `loadLanguages(File directory)`** load one file or every file
  in a directory (creating the directory first if missing).
- **`createLanguage`** (`BaseI18nBuilder.java:160-167`) dispatches on file extension:
  `.json` → `JsonLanguage`, `.lang` → `LangLanguage`, **anything else — not only
  `.yml` — falls through to `YamlLanguage`.**
- **`getLanguageCode(File)`** is the filename minus extension. `en.yml` and `en.json`
  therefore collide on the code `en`.
- **`loadLanguage`** (`BaseI18nBuilder.java:146-153`) is first-write-wins: if a language
  with the same code is already registered, the call is a no-op — so of two colliding
  files, whichever loads first (directory-listing order) wins and the other is silently
  ignored.
- **`loadLanguage(Plugin, String)`** (`BaseI18nBuilder.java:176-190`) copies a bundled
  plugin resource into the data folder (if not already present), mirrors it under
  `defaults/`, and loads the on-disk copy using the mirrored bundled copy as its default
  language (see [mergeDefaultStrings](languages.md) on the Languages page). It **throws
  `NullPointerException`, deliberately and with a clear message,** if the plugin has no
  such resource.
- **`getDefaultLanguage()`** (`BaseI18nBuilder.java:205-209`) throws
  `NullPointerException` if no default language code was set, or if it does not match a
  loaded language.

`PluginI18nBuilder` (`i18n/src/main/java/me/wyne/wutils/i18n/PluginI18nBuilder.java:16`)
resolves both the language set and the default language from a `Plugin`'s data folder
and `config.yml`, rather than requiring the caller to supply them. Its `build()`
override runs, in order: `loadLanguages()` (everything under `<dataFolder>/lang`), then
`loadDefaultLanguage()` (reads the `lang` key from the plugin's live config, falling
back to the bundled default config/language if absent or unresolved), then
`super.build()`. **This load-then-resolve order is required** — resolving the default
language first would not see languages that only exist on disk yet.

## The global instance

`I18n.global` (`I18n.java:47`) is a public, non-final, **uninitialized** static field —
`null` until a consumer assigns it. This is a deliberate contrast with `Config.global`
and `JsonRegistry.global` in the `config` and `json` modules, which are pre-constructed
and always safe to use.

Several static helpers dereference `I18n.global` unconditionally and throw
`NullPointerException` if it was never set:
`Placeholder.replace(String, Component)`,
`TextReplacement#asComponentReplacement()`, `ComponentReplacement#asTextReplacement()`,
`I18n.styleMap(Component, String)`, and `I18n.style(Component, String, String)` — see
[Replacements](replacements.md) for the first three.

## How a lookup flows end to end

The typical entry point is `I18n#accessor(Object localeContainer, String path)`
(`I18n.java:121-140`), which:

1. Resolves a `Locale` from `localeContainer` via `I18n.toLocale` — this recognizes only
   `Player` (returning its `locale()`); anything else yields `null`.
2. Resolves a `Language` via `getLanguage(Locale)` (`I18n.java:86-96`): if
   `usePlayerLanguage` is `false`, or the locale is `null`/empty/unmatched, this always
   returns the configured default language.
3. Looks up (and, if absent, creates and caches) a `LocalizationAccessor` for
   `(language, path)` in a Guava `Table` — see [Accessor caching](#accessor-caching)
   below.

From there, calling `getString`/`getComponent`/`getStringList`/`getComponentList` (and
their placeholder-expanding variants) on the accessor delegates to the configured
`StringInterpreter`/`ComponentInterpreter`, which resolves the raw text through the
`Language`.

### The two views of a language file

`Language` exposes the same underlying file two ways, and both resolve **dotted nested
paths** at any depth:

- **`getStringMap()`** — a flat `Map<String, String>` of every string in the file, keyed
  by its full path. Single-value lookups go through this.
- **`getStrings()`** — a `LanguageStrings` view used for list lookups (`getStringList`,
  `isList`) and existence checks.

So `messages.welcome` resolves identically whether it holds a single string or a list.
The two views differ only in what they carry: `getStringMap()` holds scalar strings,
while lists are reached through `getStrings()`. See [Languages](languages.md) for how
each format builds them.

### Accessor caching

`I18n#accessor` picks between `ListLocalizationAccessor` and `StringLocalizationAccessor`
based on `language.getStrings().isList(path)` **once**, the first time that
`(language, path)` pair is looked up, and caches the choice in an unbounded
`HashBasedTable` (`I18n.java:52`) for the lifetime of the `I18n` instance. Two
consequences:

- If a language file changes shape at that path at runtime (a string becomes a list, or
  vice versa) without the `I18n` instance being rebuilt, the cached accessor kind does
  not follow — lookups keep using whichever kind was cached first.
- The table is a plain `HashBasedTable`, **not thread-safe**, and never evicts entries.

### Per-player language selection

`usePlayerLanguage` (default `true`, set via `BaseI18nBuilder#setUsePlayerLanguage`)
gates whether `getLanguage(Locale)` ever returns anything other than the default
language. When it is `false`, every lookup — regardless of who it's for — resolves
against the default language only. `I18n.toLocale` (`I18n.java:211-215`) only recognizes
a `Player` argument; anything else (including an `OfflinePlayer` or a `CommandSender`
that isn't also a `Player`) resolves to `null` and therefore the default language too.

## Working example

A language file at `lang/en.yml`:

```yaml
greeting: '<gray>Welcome, <gold><player></gold>! You have <count> new messages.'
messages:
  farewell: '<gray>Goodbye, <player>.'
  motd:
    - '<green>Server rules'
    - '<green>Be nice to <player>'
```

### Typical plugin setup

Inside a plugin, `PluginI18nBuilder` is the normal entry point — it knows how to pull
language files out of the jar and how to find the default language, so neither is
hardcoded:

```java
I18n.global = new PluginI18nBuilder(plugin)
        .setLogger(logger)
        .setComponentAudience(new BukkitComponentAudiences(BukkitAudiences.create(plugin)))
        .setComponentInterpreter(ComponentInterpreters
                .valueOf(plugin.getConfig().getString("serializer", "MINI_MESSAGE"))
                .get(new EmptyValidator()))
        .setUsePlayerLanguage(plugin.getConfig().getBoolean("usePlayerLanguage", true))
        .loadLanguage("lang/en.yml")
        .build();
```

Line by line:

- **`setComponentAudience(new BukkitComponentAudiences(BukkitAudiences.create(plugin)))`**
  opts out of the `PaperComponentAudiences` default, so the plugin works on servers
  without native Adventure. It requires `adventure-platform-bukkit` at runtime, which
  this module only declares `compileOnly` — the plugin must ship or depend on it. See
  [Localized Values and Access](localized.md).
- **`ComponentInterpreters.valueOf(...)`** lets the server owner pick the markup flavor
  from config by enum name (`MINI_MESSAGE`, `LEGACY`, `ENHANCED_LEGACY`, or the three
  `ITEM_*` variants). An unrecognized name throws `IllegalArgumentException` out of
  `valueOf`, so a typo in config fails at startup rather than silently falling back.
- **`loadLanguage("lang/en.yml")`** reads a language *bundled in the plugin jar*. It
  copies the resource to `<dataFolder>/lang/en.yml` if absent, keeps a pristine copy
  under `<dataFolder>/defaults/`, and registers it under the code `en` — the file name
  minus extension, with the `lang/` prefix dropped. A missing resource throws
  `NullPointerException` with an explicit message.
- **`build()`** then does two things before constructing the `I18n`: it scans
  `<dataFolder>/lang` for every other language file an admin has dropped in, and only
  then resolves the default language from the plugin config's `lang` key (falling back
  to the bundled `config.yml`'s value). That order matters — resolving first would not
  see the on-disk files.

Note there is no `setDefaultLanguageCode` call: `PluginI18nBuilder` derives it from
config. Reach for `setDefaultLanguageCode` only with the plain `BaseI18nBuilder`.

### Reading strings back out

Away from a plugin — in a test, or when you want to point at a directory yourself — the
plain `BaseI18nBuilder` does the same job with the two config-driven steps spelled out.
That is what produced the output below:

```java
I18n i18n = new BaseI18nBuilder<>()
        .setComponentInterpreter(new MiniMessageInterpreter(new EmptyValidator()))
        .loadLanguages(new File(plugin.getDataFolder(), "lang"))
        .setDefaultLanguageCode("en")
        .build();
I18n.global = i18n;

TextReplacement who  = Placeholder.replace("player", "Wyne");
TextReplacement both = who.then(Placeholder.replace("count", 3));

i18n.accessor("greeting").getString(both).get();
i18n.accessor("messages.farewell").getString(who).get();
i18n.accessor("messages.motd").getStringList(who);
```

produces, respectively:

```text
<gray>Welcome, <gold>Wyne</gold>! You have 3 new messages.
<gray>Goodbye, Wyne.
[<green>Server rules, <green>Be nice to Wyne]
```

`messages.farewell` and `messages.motd` are nested paths and resolve the same as the
top-level `greeting` — see [the two views](#the-two-views-of-a-language-file).
`.then(...)` chains replacements left to right. Note that `getString` returns a
`LocalizedString`, not a `String`; `get()` unwraps it. A `PluginI18nBuilder` would
replace the `loadLanguages`/`setDefaultLanguageCode` calls by reading `lang` from the
plugin config.

### `TextReplacement` vs. `ComponentReplacement`

Both substitute a `<key>` placeholder, but they act at different stages, and the
difference is not cosmetic.

A `TextReplacement` runs against the **raw string, before the interpreter parses it**:

```java
i18n.accessor("greeting").getComponent(both);
```

A `ComponentReplacement` runs against the **already-built `Component`**, so it can
insert real styled components rather than markup:

```java
ComponentReplacement fancy = ComponentPlaceholder.replace("player",
        Component.text("Wyne").color(NamedTextColor.AQUA));

i18n.accessor("greeting").getComponent().replace(fancy);
```

which serializes back to:

```text
<gray>Welcome, <aqua>Wyne</aqua>! You have \<count> new messages.
```

Two things to read off that output. The `<player>` placeholder took the aqua styling
from the inserted component rather than the `<gold>` tags around it, and the
still-unreplaced `<count>` comes back **escaped** as `\<count>` — MiniMessage escapes
literal angle brackets when re-serializing, so an unsubstituted placeholder is visible
in serialized output but harmless in the rendered component.

**The stage difference decides whether a value can inject markup.** Substituting the
same hostile value `<red>Evil` both ways, then rendering as plain text:

```text
TextReplacement       -> Welcome, Evil! You have <count> new messages.
ComponentReplacement  -> Welcome, <red>Evil! You have <count> new messages.
```

The `TextReplacement` value was spliced into the raw string and then **parsed by the
interpreter**, so `<red>` was consumed as a real color tag and vanished from the text.
The `ComponentReplacement` value was inserted after parsing, so it stayed literal.

Prefer `ComponentReplacement` for anything player-supplied — names, chat input, book
text. Use `TextReplacement` for trusted values, or when you deliberately want the
substituted text to carry markup. `ComponentPlaceholder` is also the safer choice for
another reason: it matches keys literally, while `Placeholder` interprets the key as a
regex (see [Replacements](replacements.md)).
